Problem Statement & Motivation
Addressing the Architectural Limitations of Traditional Fitness Trackers
In-Memory Computation Bottleneck
Conventional web trackers haul large arrays of unindexed raw logs into application runtime memory, executing slow JavaScript loops to compute weekly totals and macro distributions.
Fragmented Biometric Silos
Step counters, meal logs, and workout diaries operate in isolation without database-level correlation between calories consumed and calories burned.
The FitPulse Engineering Solution
  • Employs hybrid document modeling balancing read locality with safe unbounded history logging.
  • Offloads analytical processing entirely to native MongoDB aggregation pipelines ($match, $group, $unwind, $lookup, $project).
  • Guarantees multi-tenant isolation, compound indexing, and zero mock data.
Theoretical Context: Document-oriented schema design versus traditional relational modeling

Database Design Philosophy — Hybrid Document Modeling
Balancing Locality of Reference with Unbounded Chronological Growth
When to Embed Documents
Child entities exist strictly within the lifecycle of the parent record and are queried together.

Example 1: Workout Sets inside Exercises within WorkoutLog. Sets have no meaning outside the session, eliminating multi-table relational joins.

Example 2: Macro Snapshots inside MealLog. Each meal item stores an immutable copy of its calories and macros at log time, isolating historical logs from future food catalog changes.
When to Reference Documents
Entities have independent lifecycles, require safe pagination, or risk unbounded document growth.

Example 1: All operational log collections reference the User collection via userId (Schema.Types.ObjectId, ref: 'User'). This enables infinite logging without hitting the 16 MB BSON document size limit.

Example 2: Reusable WorkoutTemplate documents and global FoodItem catalog entries exist independently of user session instances.
Design Rule: Favor embedding for 1-to-few bounded relationships; favor referencing for 1-to-many unbounded timelines

Detailed Schema Architecture — The 10 MongoDB Collections
Formally Typed Document Schemas with Relational Constraints
Identity & Daily Activity Collections
1. users: name, email (unique), passwordHash (select: false), height, weight, activityLevel, fitnessGoal, embedded preferences.
2. activity_logs: userId, date (YYYY-MM-DD), steps, distanceKm, estimatedCaloriesBurned, source. Unique index on (userId, date).
3. food_items: name, category, servingSize, servingUnit, calories, protein, carbs, fat, fiber. Full-text search index.
4. meallogs: userId, date, mealType, embedded items array with calculated macros, totalCalories.
Exercise, Recovery & Target Collections
5. workoutlogs: userId, date, workoutType, durationMinutes, embedded exercises with sets (reps, weightKg), MET calories burned.
6. sleep_logs: userId, sleepStart (ISO UTC), sleepEnd (ISO UTC), durationMinutes, quality (1-5), notes.
7. water_logs: userId, timestamp (ISO UTC), amountMl.
8. body_measurements: userId, date, weightKg, waist, hip, chest, arm, thigh cm.
9. goals: userId, goalType, targetValue, unit, effectiveFrom, isActive.
10. workout_templates: userId, name, category, embedded routine exercises.
Schema Validation: Enforced via Mongoose ODM types and runtime Zod schemas

Indexing Strategies & Query Optimization
Eliminating Collection Scans (COLLSCAN) via Compound & Text Indexes
Single-Field Unique Indexes
users { email: 1 }
Enforces unique user identity.
Provides O(1) B-tree lookup time during authentication.
Compound Unique Indexes
activity_logs { userId: 1, date: -1 }
Guarantees exactly one step record per day per user.
Optimizes descending chronological range queries.
Full-Text Search Indexes
food_items { name: 'text', category: 'text' }
Powers keyword search across 45+ catalog items including Indian staples with language stemming.
Additional Compound Query Indexes
meallogs: { userId: 1, date: -1 } and { userId: 1, mealType: 1, date: -1 }
workoutlogs: { userId: 1, date: -1 } | sleep_logs: { userId: 1, sleepStart: -1 } | water_logs: { userId: 1, timestamp: -1 }
body_measurements: { userId: 1, date: -1 } | goals: { userId: 1, goalType: 1, isActive: -1 }
Index Verification: All production query paths utilize IXSCAN instead of full collection scans

MongoDB Aggregation Framework (Part 1)
Operational Biometric Pipelines (Pipelines 1 through 4)
Pipeline 1: Weekly Step Analysis
Collection: activity_logs
Stages: $match (userId, date range) -> $group by calendar day with $sum on steps and distanceKm -> $project ($round) -> $sort date ascending.
Summary Facet: $group with $max, $min, and $avg.
Pipeline 2: Nutrition & Macro Distribution
Collection: meallogs
Stages: $match (userId, date) -> $group by mealType with $sum on totalCalories, totalProtein, totalCarbs, totalFat -> $project.
Generates donut chart data for macro percentages.
Pipeline 3: Training Volume Analysis
Collection: workoutlogs
Stages: $match -> $unwind '$exercises' -> $unwind '$exercises.sets' -> $project setVolume ($multiply reps by weightKg) -> $group by exerciseName with $sum -> $sort descending -> $limit 10.
Pipeline 4: Sleep Variance & Consistency
Collection: sleep_logs
Stages: $match -> $group with $avg on durationMinutes, $avg on quality, and $stdDevPop on durationMinutes -> $project consistency index (100 minus variance factor).
Key Operators: $match, $group, $sum, $avg, $unwind, $multiply, $stdDevPop, $round, $project, $sort
Slide 8 of 10
MongoDB Aggregation Framework (Part 2)
Advanced Cross-Collection Joins & Habit Scoring (Pipelines 5 through 8)
Pipeline 5: Calorie Balance Analysis ($lookup Join)
Base Collection: activity_logs
Stages: $match on userId -> $lookup from meallogs matching composite key (userId + date) -> $lookup from workoutlogs matching composite key (userId + date) -> $project daily caloriesConsumed from meallogs, walkingBurned from activity_logs, and workoutBurned from workoutlogs -> $project netBalance = caloriesConsumed - (walkingBurned + workoutBurned).
Pipeline 6: Monthly Progress
Uses $substr on date string (YYYY-MM) -> $sum on steps and workouts -> computes net weight change (lastWeight - firstWeight).
Pipeline 7: Activity Leaderboard
Groups 7-day steps across users -> $lookup on users -> $project anonymized name ($concat firstName, space, $substrCP lastName, '.').
Pipeline 8: Consistency Score
Algorithmic habit index (0-100) weighting: Steps (25%), Workouts (25%), Sleep (20%), Hydration (15%), Nutrition (15%).
Advanced Operators: $lookup sub-pipelines, $expr, $arrayElemAt, $substr, $concat, $substrCP

Security, Multi-Tenant Isolation & Data Integrity
Defense-in-Depth Mechanisms across Application and Database Layers
Multi-Tenant User Isolation
The authenticated user's ObjectId is extracted from the cryptographically verified JWT token in middleware (req.user.id).

Every private query strictly enforces an explicit filter: { userId: req.user.id }.

Users cannot read, modify, or delete records belonging to other athletes.
Cryptographic Authentication & Cookies
Passwords are hashed with bcrypt (salt factor 10) and marked select: false in Mongoose models.

Signed JWT tokens (7-day TTL) are stored in secure HttpOnly cookies, mitigating XSS token theft.
Input Validation & NoSQL Injection Defense
Strict Zod schemas validate data types, date formats, and numerical bounds before database queries execute.
Cascading Account Deletion
Deleting an account coordinates deleteMany operations across all ten collections, eliminating orphaned records.
Security Standard: Defense-in-depth preventing injection, privilege escalation, and data corruption
